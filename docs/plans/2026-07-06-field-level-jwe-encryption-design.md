# 민감 필드 전송 구간 암호화 (JWE) 설계

## 배경 및 목적

React 앱과 백엔드 API(Java/Spring) 사이에서 개인정보 등 민감 필드가 네트워크 상에 평문으로 노출되는 것을 방지한다.

- **목적**: 규제 대응(개인정보 필드 암호화 요건), 로그/중간 인프라(게이트웨이, 프록시 등)에서의 평문 노출 방지
- **비목적**: DB 레벨 암호화는 대상 아님. HTTPS를 대체하는 것이 아니라 보완하는 계층임
- **범위**: 전체 트래픽이 아닌, 지정된 특정 민감 필드만 대상. 특정 화면에 종속되지 않는 범용 유틸리티로 설계

## 왜 HTTPS만으로는 부족한가

HTTPS(TLS)는 클라이언트-서버 간 네트워크 경로의 도청자를 막지만, 다음 지점에서는 평문이 실제로 존재한다:
- TLS를 종료하는 로드밸런서/API 게이트웨이/WAF
- 그 지점들에서 남는 액세스 로그, APM 도구 등

필드 레벨 JWE 암호화는 이 지점들에서도 민감 필드가 평문으로 보이지 않도록, "복호화 가능한 개인키를 가진 최종 처리 계층"까지 암호문 상태를 유지한다.

## 아키텍처

- **표준**: JWE (RFC 7516)
- **알고리즘**: 키 래핑 `RSA-OAEP-256`, 콘텐츠 암호화 `A256GCM`
- **키 구성**:
  - **서버(Spring) 장기 키쌍**: `GET /api/crypto/public-key`로 공개키 노출. 요청 필드 암호화에 사용 (프론트가 이 공개키로 암호화 → 서버가 개인키로 복호화)
  - **클라이언트 임시 키쌍**: 세션(페이지 로드)마다 브라우저에서 생성, `extractable: false`로 생성해 개인키 원본이 메모리 밖으로 추출 불가능하게 함. 응답 필드 암호화에 사용 (프론트가 요청에 공개키를 동봉 → 서버가 그 공개키로 응답 암호화 → 프론트가 자신의 개인키로 복호화)

서버가 고정 키 하나만으로 응답을 암호화하면 그 공개키로 암호화한 응답은 서버 자신만 복호화 가능해 의미가 없으므로, 응답 방향은 반드시 클라이언트 임시 키쌍이 필요하다.

## 데이터 흐름

1. 앱 초기화: 프론트가 서버 공개키를 fetch해 캐시하고, 자신의 임시 RSA 키쌍을 생성
2. 요청 시: 지정된 민감 필드만 서버 공개키로 JWE 암호화, 클라이언트 공개키(JWK)를 요청에 동봉. 나머지 필드는 평문 그대로
3. 서버: 개인키로 필드 복호화 → 비즈니스 로직 처리
4. 응답 시: 지정된 응답 필드를 요청에서 받은 클라이언트 공개키로 JWE 암호화
5. 프론트: 자신의 임시 개인키로 응답 필드 복호화 후 화면에 표시

## 컴포넌트 (프론트엔드, 이 레포 작업 범위)

범용 유틸리티로 설계하며, 특정 화면에 종속된 필드 목록은 이 설계에 포함하지 않는다. 실제 사용 시 각 RTK Query 엔드포인트가 필요한 필드명을 선언한다.

- `shared/lib/crypto/serverPublicKey.ts`
  서버 공개키 fetch 및 세션 내 캐시. `kid`(키 버전) 불일치 시 캐시 무효화 후 1회 재시도.
- `shared/lib/crypto/clientKeyPair.ts`
  세션당 1회 임시 RSA-OAEP 키쌍 생성 및 모듈 싱글턴으로 보관 (`extractable: false`). 페이지 새로고침 시 폐기 후 재생성.
- `shared/lib/crypto/jwe.ts`
  `jose` 라이브러리 기반 `encryptFields(payload, fieldNames, publicKey)` / `decryptFields(payload, fieldNames, privateKey)`.
- `axiosBaseQuery` 확장
  엔드포인트 `query()` 설정에 `encryptedFields: string[]`를 선언하면 요청/응답 인터셉터가 자동으로 암복호화 처리. 개별 화면 코드 변경 불필요.

백엔드(Spring)는 이 레포 범위 밖이며, `nimbus-jose-jwt` 기반으로 동일한 JWE 처리(공개키 엔드포인트, 요청 복호화, 응답 암호화)를 구현한다고 가정한다.

## 에러 처리 원칙

- 공개키 fetch 실패, Web Crypto API 미지원, 복호화 실패 시 **평문 폴백 금지** — 요청 자체를 막거나 명시적 에러로 표시
- 서버 `kid` 불일치 시 캐시된 공개키 무효화 후 1회 재fetch 후 재시도, 그래도 실패하면 에러 처리

## 테스트 전략

- `jose` 기반 encrypt/decrypt 유틸의 라운드트립 단위 테스트
- MSW로 서버 공개키 + 에코 API를 목킹해, 실제 axios 요청 바디에 지정 필드가 평문으로 실리지 않는지 네트워크 레벨에서 검증
